## 1. これは何か

日付を入れると、**西暦と和暦を相互に変換する** Chrome 拡張機能。主方向は西暦→和暦。

単一用途の説明（Chrome Web Store 審査で提出する文）：

> 入力またはページ上で選択した日本の暦日を、西暦と和暦の間で改元日まで検証して正確に変換する拡張機能です。

## 2. なぜ作るか — 既存4本との違い

Chrome ウェブストアには和暦変換の拡張が少なくとも4本ある（和暦変換／和暦⇄西暦コンバータ／daisy WarekiConv／和暦アドオン for SalesForce）。**この領域は空白ではない。**

差別化の1文：

> 改元日の境界を検証して正確な和暦を返し、**改元のあった年は境界日を注記で示す**。全角・元年・略号・曜日付きの入力を受理し、存在しない和暦を作らない和暦変換拡張。

肯定形の中核は**注記**である。既存4本は「1989年は1月7日までが昭和64年、1月8日からが平成元年」を能動的に教えない。ユーザーが `昭和64年1月8日` という存在しない和暦を思い浮かべる場面（実際に本件の発注者がそう述べた）で、正解と理由を同時に示せることが本拡張の価値である。

**なお、競合が4本あることは「最小機能性ポリシー」の論点ではない。**最小機能性が問うのは「その拡張が実質的な機能を持つか」（ブックマークレット同然か、単一サイトのラッパーか）であり、本拡張はパーサー・コンテキストメニュー・通知を備えた独立実装なのでこの基準は明確に満たす。競合4本に対する差別化が効いてくるのは「ユーザーが選ぶ理由」の方である。

## 3. 拘束要件

| # | 要件 |
|---|---|
| R1 | 西暦から和暦を逆算する。これが主機能 |
| R2 | 変換対象は日付全体（年月日）。年だけではない |
| R3 | 既存の「年齢・年度計算」拡張とは別アプリとする |
| R4 | **改元のあった年の日付は「主たる和暦＋注記」形式で表示する**（6-4節） |

## 4. 対象外

年齢、年度、学年、祝日、旧暦変換、ページ全体の自動書き換え、変換履歴、クラウド同期。

## 5. 変換方向

双方向。主方向は西暦→和暦、補助方向は和暦→西暦。ポップアップでは方向を明示的に切り替え、自動推定だけに依存しない。右クリックでは入力形式から方向を判定し、どちらにも完全一致しない場合は推測しない。

双方向にする理由は、検証済みドメイン層で既に成立しており、追加の権限も外部機能も要らず、「暦日の相互変換」という1文の単一用途を維持できるため。

受入条件：

- `平成元年1月8日` および `H元.1.8` は `1989年1月8日` になる
- `平成元年1月7日` は変換せず「平成の期間外」と境界日を示す
- 方向を切り替えても、同じ暦日を往復変換した結果が一致する

## 6. ドメイン要件と受入条件

### 6-1. 元号データ

| 元号 | 開始日 |
|---|---|
| 明治 | 1868-01-25 |
| 大正 | 1912-07-30 |
| 昭和 | 1926-12-25 |
| 平成 | 1989-01-08 |
| 令和 | 2019-05-01 |

境界日は新元号側に含める。元号年は `西暦年 - 開始年 + 1`。初年は「元年」と表記する。終了日は持たず、次の元号の開始日から導出する。

**開始日は元号年計算の基点であり、入力受理下限（6-3節）とは別概念である。**明治の開始日を 1873-01-01 に動かすと明治年が全件5年ずれる（明治6年 = 1868+6−1 = 1873 が正しい）。データから 1868-01-25 を消してはならない。

**元号名・略号の列挙は `ERAS` から動的に生成する。**正規表現に `(明治|大正|昭和|平成|令和)` や `[MTSHR]` をハードコードしない。改元時に「正規表現の列挙だけ更新し忘れる」のが最も起きやすい事故であるため。

受入条件（境界の前日と当日）：

| 西暦 | 和暦 |
|---|---|
| 1912-07-29 | 明治45年7月29日 |
| 1912-07-30 | 大正元年7月30日 |
| 1926-12-24 | 大正15年12月24日 |
| 1926-12-25 | 昭和元年12月25日 |
| 1989-01-07 | 昭和64年1月7日 |
| 1989-01-08 | 平成元年1月8日 |
| 2019-04-30 | 平成31年4月30日 |
| 2019-05-01 | 令和元年5月1日 |

### 6-2. 入力形式

受理する：西暦4桁の年月日（`1989年1月8日` `1989/1/8` `1989-1-8` `1989.1.8`）、漢字元号（`平成元年1月8日` `平成1年1月8日`）、元号略号（`H1.1.8` `H元/1/8`、大文字小文字問わず）、NFKC で正規化可能な全角、単一の短い先頭ラベル（`生年月日：1987年5月14日`）、曜日括弧、定義済みの末尾補助語・約物。

受理しない：**年のみ**（`1989年`）、年月のみ、月日のみ、複数日付、2桁西暦、漢数字、区切りなし8桁、月日年順、区切り記号の混在、実在しない日付、元号期間外、明治5年以前、長すぎる入力。

**年のみを受理しない理由**：`1989年` の正解が昭和64年と平成元年の2つになり、主機能である「日付全体の正確な変換」と矛盾する。エラーは「改元年は元号を一意に決められないため、月日まで入力してください」とする。

### 6-3. 対応期間

**下限は 1873-01-01（明治6年1月1日）。**明治5年以前は旧暦（天保暦）であり、元号年から西暦への機械換算が成立しない。`明治元年2月1日` は実際にはグレゴリオ暦 1868-02-23 だが、機械換算では 1868-02-01 となり約3週間ずれる。誤った出力は明示エラーより悪い。

エラーには旧暦が理由であることと下限日を示す。

### 6-4. 改元年の注記（拘束要件 R4）

**同じ西暦年が2つの元号にまたがる場合のみ**、その事実を注記で示す。

表示例：

```
入力：1989/1/8

  平成元年1月8日
  1989年1月8日
  ──────────────────
  ※ 1989年は1月7日までが昭和64年、
     1月8日からが平成元年
```

```
入力：1989/1/7

  昭和64年1月7日
  1989年1月7日
  ──────────────────
  ※ 同一の注記
```

**その日付の正しい和暦だけを主表示とする。存在しない和暦（`昭和64年1月8日`）を併記しない。**

**判定式**：

```
注記を出す条件：ある元号 e について
  previousDay(e.start).year === 対象年  かつ  e.start.year === 対象年
```

`e.start.year === 対象年` だけで判定してはならない。将来 1 月 1 日開始の元号が現れた場合、その年は前元号が前年12月31日で終わるため1元号しか含まないが、素朴な式では「2元号にまたがる」と誤判定する。また同一年内に2回改元される事態に備え、条件に合う元号を**すべて**列挙して注記を組み立てる。

**文言生成**：`e` を対象年に開始した元号、`p = previousDay(e.start)`、`prev` を `p` が属する元号として、

> `{対象年}年は{p.month}月{p.day}日までが{prev.name}{eraYearLabel}年、{e.start.month}月{e.start.day}日からが{e.name}元年`

受入条件：

| 入力 | 主表示 | 注記 |
|---|---|---|
| `1989/1/8` | 平成元年1月8日 | あり |
| `1989/1/7` | 昭和64年1月7日 | **同一の注記** |
| `1989年12月25日` | 平成元年12月25日 | **あり**（境界から遠くても同じ年なら出す） |
| `1990/1/1` | 平成2年1月1日 | なし |
| `1912/7/29` | 明治45年7月29日 | 7月29日までが明治45年、7月30日からが大正元年 |
| `1926/12/25` | 昭和元年12月25日 | 12月24日までが大正15年、12月25日からが昭和元年 |
| `2019/4/30` | 平成31年4月30日 | 4月30日までが平成31年、5月1日からが令和元年 |

**和暦→西暦方向でも同じ注記を出す。**方向によって注記の有無が変わる合理的理由がない。

### 6-5. 改元データの確認期限

外部通信をしない以上、未更新の拡張が改元の発生を自動検知することは不可能である。

**確認期限（`verifiedThrough`）を超える日付でも変換は行い、警告注記を付す。**

```
  令和12年4月1日
  2030年4月1日
  ──────────────────
  ※ この日付は同梱の元号データ確認期限より後です。
     以降に改元があった場合、正しい和暦は異なります。
```

**変換を停止してはならない。**Stage 1 の設計は停止する案だったが、Stage 2 の査読で覆した。理由は失敗の非対称性である。誤変換のリスクは「改元が起きたとき、改元日以降の日付についてのみ」発生するのに対し、停止のコストは「改元が起きなくても、期限以降のすべての日付」に発生する。契約満了日・有効期限・満期日など数年〜数十年先の日付は和暦変換の主要用途であり、これを丸ごと落とす代償に見合わない。

加えて、確認期限はビルド時に凍結される値である。更新が止まれば時間の経過だけで「今日の日付が変換できない和暦変換拡張」が完成する。これは既知不具合パターン1（時刻のハードコード）の変種である。

**値は絶対日付をハードコードせず、`ERAS` の最新元号開始日から導出できる相対規則で持つ。**

**この規則は双方向に適用する。**西暦→和暦だけでなく、和暦→西暦（`令和50年1月1日` → `2068年1月1日`）にも同じ警告を出す。最新元号には次の元号が無いため `isWithinEra` が無条件 true を返すので、パーサー側に別途ガードが要る。

### 6-6. 未来上限の一本化

流用元には未来方向の上限が3つ同居している。**1つに統合する。**

| 定数 | 流用元での挙動 | 本拡張での扱い |
|---|---|---|
| `WAREKI_DISPLAY_HORIZON_YEARS = 100` | 最新元号開始年+100年まで無条件に和暦を返す（2119年まで「令和101年」を返す） | **廃止** |
| `MAX_REFERENCE_DATE = 2200-12-31` | パーサーから未参照の死んだ定数 | **廃止または入力上限として明示的に参照** |
| `verifiedThrough` | 新規 | **これに一本化** |

`WAREKI_DISPLAY_HORIZON_YEARS` を残したまま移植すると、「無警告で `令和XX年` を返さない」という本拡張の方針に真正面から反する。

### 6-7. 複数日付の検知

**候補数は2点で数える。**

- (a) NFKC + trim の直後（情報を捨てる除去処理の**前**）
- (b) 全正規化後

**`max(a, b) >= 2` なら `MULTIPLE_DATES`。**0件は許容する（完全一致検査に委ねる）。

片方だけで数えてはならない。NFKC 前で数えると、JavaScript の `\d` が ASCII のみを対象とするため**全角の2日付入力が素通りする**（`生年月日：１９８７年５月１４日 登録日：２０２０年１月１日` は NFKC 前の候補数が0件）。逆に「前後の候補数が一致すること」を要求すると、`1987年 5月 14日` や `1987 / 5 / 14`（空白除去前0件、除去後1件）を誤って拒否する。

### 6-8. 先頭ラベルの除去

**最初のコロン**より前が、数字・元号名・日付区切りを含まない許可長以内の文字列であり、**かつコロン以後の日付候補がちょうど1件**の場合にのみ除去する。

この規則は姉妹拡張（年齢アプリ）で発見された不具合への対策である。`lastIndexOf(":")` により最後のコロン以降を無条件に採用していたため、`生年月日：1987年5月14日 登録日：2020年1月1日` が `2020年1月1日` として無警告で受理されていた。**完全一致検証を後段に置いていても、前処理が先に情報を捨てるため防げない。**

ラベルに元号名を含むものを拒否する（`平成元年:1987年5月14日` の誤受理を塞ぐため）。副作用として `平成生まれ：1987年5月14日` のような自然なラベルも拒否されるが、誤受理ではなく誤拒否なので安全側である。**意図的挙動として受入条件に明記しテストで固定する。**

区切り記号が2個以上ある場合は `MULTIPLE_DATES` ではなく別コードとする（`メモ:生年月日:1987年5月14日` は日付が1件しかないのに「日付は1件だけ指定してください」と出るのは誤りであるため）。

### 6-9. 存在しない和暦への「もしかして」提案

`昭和64年1月8日` のような存在しない和暦を入力した場合、期間外エラーを返すだけでなく、**機械換算した西暦が実在日であれば正解を併記する。**

> 昭和64年1月8日は昭和の期間外です。昭和は1926年12月25日開始、平成は1989年1月8日開始です。
> **この日付は 平成元年1月8日 です。**

拘束要件 R4 の経緯そのものが示すとおり、「平成元年（昭和64年）」という直感を持つ利用者は実在する。注記機能と実装を共有できるため追加コストは小さい。

## 7. 入力経路と出力

### 7-1. ポップアップ

テキスト入力、変換方向、変換ボタン、結果、コピー、入力例、エラー領域。初回フォーカスは入力欄。Enter で変換、方向切替はキーボード操作可能、Esc で閉じる。結果は選択可能なプレーンテキストとして表示する。

**コピー対象は和暦＋西暦の2行のみとし、注記を含めない。**入力の余分なラベル等も含めない。

`navigator.clipboard.writeText()` を追加権限なしで試す。失敗時は結果を選択状態にして手動コピーを案内する。`clipboardWrite` は要求しない。

### 7-2. 選択テキストの右クリック

メニュー名は「選択した日付を和暦・西暦変換」。ページを書き換えず Chrome 通知で結果またはエラーを返す。同一通知IDを再利用して積み上げない。

**通知は主表示のみとし、注記はポップアップで見せる。**通知本文は OS により2行程度で切られるため、注記を入れると主表示が埋もれる。

通知が拒否されている場合、結果を `storage.session` に一時保存してバッジを `!` にし、ポップアップで確認するよう案内する。

### 7-3. `selectionText` の改行欠落への対処

`info.selectionText` は段落区切りの改行を保持しない（既知不具合パターン12）。`window.getSelection()` での再取得は**採用しない**——`scripting` かページ注入が必要になり、制限ページで失敗し、最小権限を損なうため。

本機能は段落構造を結果生成に使わない。連結された複数日付を単一日付と解釈しないことは、6-7 の候補数検査と完全一致検証で担保する。

## 8. 非機能要件

### 8-1. 権限

`contextMenus`・`storage`・`notifications` のみ。`host_permissions`・`activeTab`・`scripting`・`tabs`・`clipboardWrite`・外部通信に関する権限は要求しない。

### 8-2. 保存

入力・結果・履歴を `storage.local` / `storage.sync` に保存しない。通知拒否時の一時結果だけを `storage.session` に置く。未知の `schemaVersion` は空状態へ変換せず、既存値を上書きしない。

### 8-3. Service Worker 再起動耐性

メモリに状態を保持しない。コンテキストメニューは `onInstalled` と `onStartup` の両方で登録する。

### 8-4. 対応できないページ

ページ注入を行わないため、`selectionText` が提供されるページでのみ動作する。`chrome://`・Chrome Web Store 等でメニューが出ない場合に備え、ポップアップ内に常設案内を置く。取得できない場合にページ注入へフォールバックしない。

### 8-5. アクセシビリティ

マウスなしで入力・方向選択・変換・結果選択・コピーまで完結する。結果領域は `aria-live="polite"`、エラーは `role="alert"`。**読み上げ順は入力→方向→実行→エラー→結果→注記→コピー**とする。色だけで成否を示さない。

### 8-6. リモートコード不使用

全コード・データを同梱する。ビルド後に外部URL参照が無いことを機械検査する。

## 9. 年齢アプリとの関係

### 9-1. 統合判定の3条件では「統合すべき」に落ちる

ai-council_v2 第3回会合で定めた統合判定（起動導線・入力・出力の宛先）を当てはめると、本アプリと年齢アプリは**3条件とも一致する**。基準どおりなら統合すべき側である。ユーザーは経緯を理解したうえで別アプリとする判断を下した。

### 9-2. 公開方針

**和暦アプリのみ Chrome Web Store へ公開し、年齢アプリは手元利用にとどめる。**

議長が事実確認した結果、**年齢アプリは Chrome Web Store に未提出**である（GitHub 公開のみ）。したがってこの方針は何も非公開化せずに実行できる。

**ただしリスクの確度は不明である。**Chrome のスパム／重複コンテンツ方針が問題にするのは「機能が重複した複数の拡張」であり、年齢アプリの主機能は年齢・年度計算、本アプリは和暦変換で、ユーザーから見た用途は異なる。UI と入力形式が似ていることは事実だが、それだけで制裁される確度を定量化する根拠は誰も持っていない。本方針は保守的な判断であり、「両方公開すると必ず制裁される」という主張ではない。

将来 Store 公開を再検討する場合の材料として、この不確実性を記録に残す。

## 10. 本要件の限界

- 競合4本の実挙動（境界日の扱い、注記の有無）は未検証である。「注記が唯一の肯定形の差別化」という判断は、既存4本が境界日の注記を出さないという推定に立つ。Store 説明文で優位性を主張する前に1〜2本の実挙動確認が要る
- `chrome.notifications` の実表示行数は OS・Chrome バージョン依存であり実機確認が必要
- 同一西暦年内に2回改元される事態は明治以降の実データに存在しない（0件）。判定式を一般形で書くのは過剰設計とも言えるが、コストがほぼゼロなので採用した
