## Stage 2 で何が起きたか

査読席は **blocker 2件・major 5件・minor 10件**を検出し、**Stage 1 の中核判断を1つ覆した。**

### 覆された判断：確認期限を超える日付の扱い

Stage 1 は「同梱の元号データの確認期限を超える日付は、最新元号を機械的に延長せず**変換を止める**」という設計だった。正確さを優先した判断である。

査読席はこれを支持せず、**失敗の非対称性**を根拠に反対した。

| | 誤変換のリスク | 停止のコスト |
|---|---|---|
| 発生条件 | 改元が**起きたとき**、改元日以降の日付のみ | 改元が**起きなくても**、期限以降のすべての日付 |
| 影響範囲 | 限定的 | 全面的 |

加えて確認期限はビルド時に凍結される値であるため、更新が止まれば時間の経過だけで「今日の日付が変換できない和暦変換拡張」が完成する。これは既知不具合パターン1（時刻のハードコード）の変種である。

決定的だったのは、ユーザーが選んだ**「事実は主表示、不確かさは注記」という形式との不整合**である。確認期限だけが停止という強い扱いを取る整合的理由がない。議長は査読席を採り、変換は続行して警告注記を付す形に変更した。あわせて値を絶対日付ではなく `ERAS` から導出する相対規則にした。

### 設計文書だけを読んでいては出ない指摘

査読席は**流用元の実コードまで読み**、`era.ts` の `WAREKI_DISPLAY_HORIZON_YEARS = 100` が **2119年まで「令和101年」を無警告で返す**ことを発見した。設計は「無警告で令和XX年を返す設計は採らない」と宣言しているのに、コピーしてくるコードがまさにそれを実装していた。しかも設計は「移植直後に差分ゼロを確認する」と書いており、**差分ゼロを達成した瞬間に設計違反になる**という自己矛盾があった。

受入手順を「差分ゼロの確認」から「差分を全件列挙し、各差分に意図の根拠を添える」へ変更した。

### 議長が確認した事実

査読席が「未確認の事実に依存している」と指摘した点を議長が確認した。**年齢アプリは Chrome Web Store に未提出**である（GitHub 公開のみ）。したがって「和暦アプリのみ Store 公開」という方針は、稼働中の製品を非公開化する必要がなく実行できる。
