### なぜコピーで、共有パッケージにしないか

2製品・個人開発という条件で npm パッケージの常設運用費は見合わない。また Store 配布物はどの方式でも製品ごとに再ビルド・再審査が要るため、共有化してもリリース作業は減らない。

**撤退条件を先に決めておく。**次のいずれかが起きたら共有パッケージ化を再検討する。

- 3製品目が同じ元号ドメインを使う
- 横断反映漏れが1回でも発生する

### 改元時に修正する箇所

「元号定義は1ファイルだけ」は**現状では正確ではない**。`eras.ts` の開始日に加えて、`EraId` の union 型、正規表現内の元号名・略号の列挙が各リポジトリにある。

**対策：元号名・略号の列挙を `ERAS` から動的生成する。**これによりコピー方式の負債を実質的に減らせる。

```ts
const ERA_NAMES = ERAS.map((e) => e.name).join("|");
const ERA_ABBRS = ERAS.map((e) => e.abbreviation).join("");
```

## 3. 改元年の注記（要件 6-4 の実装）

新規モジュール `domain/era-transition.ts`。既存の `eraForDate` / `eraYearOf` / `eraYearLabel` / `previousDay` の組み合わせで書ける。**新規の暦計算は不要。**

```ts
type EraTransition = Readonly<{
  year: number;
  previousEra: EraDefinition;
  previousEraLastDay: PlainDate;
  nextEra: EraDefinition;
}>;

/** 対象年に改元があれば、その情報をすべて返す（同一年内の複数改元に備える） */
export function transitionsInYear(year: number): readonly EraTransition[];
```

判定式（要件 6-4）：

```ts
ERAS.filter((e) => {
  const prevDay = previousDay(e.start);
  return e.start.year === year && prevDay.year === year;
})
```

`e.start.year === year` だけで判定してはならない。将来 1 月 1 日開始の元号が現れると、その年は前元号が前年12月31日で終わるため1元号しか含まないが、素朴な式では2元号にまたがると誤判定する。

文言生成は `presentation/format-result.ts` で行う（ドメイン層は文言を持たない）。

## 4. 確認期限（要件 6-5 の実装）

`eras.ts` に置く。**絶対日付をハードコードしない。**

```ts
/** 最新元号の開始日から何年先までを「確認済み」とみなすか */
export const VERIFIED_YEARS_AFTER_LATEST_ERA = 30;

export function verifiedThrough(): PlainDate {
  const latest = ERAS[ERAS.length - 1]!;
  return { year: latest.start.year + VERIFIED_YEARS_AFTER_LATEST_ERA, month: 12, day: 31 };
}
```

導出可能な形にすることで、改元時に `ERAS` へ1行追加すれば確認期限も自動的に前進する。更新漏れで製品が壊れない。

**双方向に適用する。**西暦→和暦では `formatWareki` の後段で、和暦→西暦では `buildFromEra` の後段で同じ判定を行う。最新元号には次の元号が無いため `isWithinEra` が無条件 true を返す。これを放置すると `令和50年1月1日` が無警告で `2068年1月1日` になり、差別化の1文に反する。

戻り値は「変換結果＋警告フラグ」とし、**変換自体は成功させる**。

```ts
type ConversionResult = Readonly<{
  gregorian: PlainDate;
  wareki: string;
  transitions: readonly EraTransition[];  // 改元年の注記用（空なら注記なし）
  beyondVerified: boolean;                // 確認期限超過の警告用
}>;
```

## 5. 入力解析（要件 6-7・6-8 の実装）

処理順序：

1. 入力長を検査
2. NFKC 正規化 + trim
3. **候補数 (a) をここで数える**（情報を捨てる前）
4. 先頭ラベル除去（条件付き。下記）
5. 曜日括弧・末尾補助語・約物の除去（変化しなくなるまで繰り返す）
6. 内部空白の除去
7. **候補数 (b) をここで数える**
8. `max(a, b) >= 2` なら `MULTIPLE_DATES`
9. 全体を許可形式に完全一致させる
10. 暦日妥当性 → 下限 → 元号期間 → 確認期限 の順に検証

**先頭ラベル除去の条件**（すべて満たす場合のみ除去）：

- **最初の**コロンより前である（`lastIndexOf` ではない）
- 許可長（12文字）以内
- 数字を含まない
- **元号名を含まない**（`平成元年:1987年5月14日` の誤受理を塞ぐ）
- コロン以後の日付候補がちょうど1件

区切り記号が2個以上ある場合は `MULTIPLE_DATES` ではなく別コードを返す。

## 6. 出力

### ポップアップ

```text
入力：1989/1/8

  平成元年1月8日        ← 主表示
  1989年1月8日          ← 副表示
  ──────────────────
  ※ 1989年は1月7日までが昭和64年、1月8日からが平成元年
```

コピー対象は主表示＋副表示の2行のみ。注記は含めない。

### 通知

`title` に主表示、`message` に副表示。**注記は載せない**（2行程度で切られ主表示が埋もれるため）。注記が必要ならポップアップへ誘導する。

通知が `denied` の場合は `getPermissionLevel()` で事前判定し、結果を `storage.session` に置いてバッジを `!` にする。`create()` はOS側で抑制されていても成功を返すため、コールバックの成否では検知できない。

## 7. 既知の不具合パターンへの対応

| パターン | 対応 |
|---|---|
| 1. 時刻のハードコード | ドメイン層は時計を参照しない。確認期限は `ERAS` から導出する |
| 2. schemaVersion の空状態 coercion | 未知バージョンは読み取り専用エラー状態にし書き戻さない |
| 3. `.catch()` 欠如 | Chrome イベントから起動する Promise に必ず終端 `.catch()` |
| 4. 貪欲マッチ／前処理での情報破棄 | **候補数の2点検査**と条件付きラベル除去（5節） |
| 9. 連打 | ハンドラ先頭で `disabled = true`。通知は世代トークンで最新のみ表示 |
| 10. 一時UIの重なり | ページ内トーストを使わない。通知は固定ID |
| 12. `selectionText` の改行欠落 | 段落構造を結果生成に使わない。`getSelection()` 再取得はしない（権限が増えるため） |

## 8. テスト戦略

### 単体テスト

要件定義の受入条件と1対1で対応させる。特に以下。

- 元号5件の開始日前日／開始日
- 元年表記と2年目への遷移
- 和暦→西暦→和暦の往復不変性
- **改元年の注記**：1912 / 1926 / 1989 / 2019 の境界前後の日と、**年内の無関係な日**（1989年12月25日）でも同じ注記が出ること。1990年など非境界年で注記が出ないこと
- **元号開始日が1月1日だった場合に注記を出さないこと**（判定式のガード）
- **確認期限超過を双方向で**（`令和50年1月1日` を含む）
- **全角コロンが NFKC で `:` になり、ラベル除去が全角入力でも同じ結果になること**
- **全角2日付入力が `MULTIPLE_DATES` になること**（NFKC 前の候補数が0でも防げること）
- **`1987年 5月 14日` / `1987 / 5 / 14` が候補数検査で誤って拒否されないこと**
- `平成生まれ：1987年5月14日` が意図的に拒否されること
- `昭和64年1月8日` に「この日付は 平成元年1月8日 です」が併記されること
- ドメイン層が `Date` / DOM / Chrome API を参照していないこと（静的検索）

### 統合テスト

ポップアップの DOM 操作、コンテキストメニューの `removeAll → create` 順序、通知IDの固定と更新、`.catch()` の終端、連打防御、`storage.session` の Service Worker 再起動後の復元、未知 schemaVersion の非上書き、通知 `denied` 時のバッジフォールバック。

### E2E

`chrome://extensions` はブラウザ自動化ツールから遮断されており実インストールを自動化できない。**手動で未パック拡張を読み込んだテストプロファイル**を事前準備し、Playwright はポップアップと通常ページに限定する。Chrome 内部ページ・OS通知・右クリックメニュー自体は手動確認。
