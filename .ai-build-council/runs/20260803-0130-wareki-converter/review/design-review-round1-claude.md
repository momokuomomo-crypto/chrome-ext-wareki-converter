## 要約

Stage 1 設計は、単一用途の定義、権限の絞り込み、既知パターン 2/3/9/10/12 への対応、Store 公開方針の三択比較まで含めて、全体として水準が高い。特に 4 節の先頭ラベル対策は、報告された `lastIndexOf(":")` 事例を実入力で追跡した結果、**既存の修正済みコードよりも一段強い**（`平成元年:1987年5月14日` のような「元号を含む短いラベル」による情報破棄を追加で塞ぐ）ことを確認した。ドメイン境界日・元号年計算式も手計算で全件一致した。

一方で、**拘束要件5 が未反映**であること、および **`verifiedThrough` の「変換を停止する」判断が主機能を壊す**ことの 2 点は、このまま実装に入ってはならない。加えて、流用元 `era.ts` に存在する `WAREKI_DISPLAY_HORIZON_YEARS = 100`（最新元号を 100 年機械延長する）が「差分ゼロでコピー」と `verifiedThrough` の双方と三つ巴で矛盾しており、設計本文はこれに一切触れていない。

## 承認 / 要修正の判定

**要修正（条件付き）。** 設計の骨格・アーキテクチャ・権限設計・テスト戦略は概ね採用可。ただし下記 blocker 2 件と major 5 件を設計文書に反映したうえで Stage 3 へ進むこと。全面書き直しは不要で、追記と 2 箇所の判断変更で足りる。

## 指摘事項（あれば、重大度つき）

- **[blocker] 拘束要件5（改元年の「主たる和暦＋注記」表示）が設計に存在しない。** 設計の出力仕様（6 節）は「結果」としか書いておらず、注記の生成規則・表示位置・通知への載せ方・コピー対象への含否がいずれも未定義。拘束要件である以上、これを書かずに実装へ渡すと要件未達が確定する。対応可否と具体的な追記内容は後述の専用節に記す（結論：**衝突なし、追加コスト小**）。

- **[blocker] `verifiedThrough` を超える日付で「変換を停止する」判断（13 節）は、製品の主機能を壊す。** 3 つ検算した。
  1. **値が未決のまま製品仕様が確定している。**設計自身が「実装前に運用可能な値へ決定する必要がある」（不確実な点）と書いており、誰がどの根拠で決めるかの規則が無い。にもかかわらず、差別化の 1 文、エラー辞書、Store 説明文がすべて「停止する」前提で書かれている。実装後に方針を変えると 3 箇所を巻き戻すことになる。
  2. **`verifiedThrough` はビルド時に凍結される。**改元が起きなくても、更新が止まった拡張は時間の経過だけで使えなくなる。仮に `2028-12-31` と置けば、2029 年 1 月 1 日に「**今日の日付が変換できない和暦変換拡張**」が完成する。改元は「起きたら誤変換」だが、確認期限は「起きなくても機能停止」であり、失敗の向きが逆。
  3. **拘束要件5 が、この問題の正解を先に示している。**ユーザーが選んだのは「存在しない和暦を併記しない／事実は主表示、不確かさは注記」という形式である。同じ思想を確認期限に適用すれば、「変換したうえで注記で警告する」が一貫解になる。停止だけが例外的に強い扱いになっている。

  **修正案**：`verifiedThrough` 超過は変換を止めず、結果に警告注記を付す。

  ```
    令和12年4月1日
    2030年4月1日
    ──────────────────
    ※ この日付は同梱の元号データ確認期限（2027年12月31日）より後です。
       以降に改元があった場合、正しい和暦は異なります。
  ```

  値の決め方も規則として書くこと。推奨は「最終公開ビルド日 + 一定年（例：2 年）を超えたら注記対象」という**相対規則**。絶対日付の直書きは既知パターン1（タイムボム）の変種であり、`eras.ts` に絶対日付を持たせるなら「最新元号の開始日 + N 年」など導出可能な形にして、更新漏れで機能が死なないようにする。

- **[major] 流用元 `era.ts` の `WAREKI_DISPLAY_HORIZON_YEARS = 100` を設計が認識していない。** `formatWareki()` は最新元号開始年 +100 年までは無条件に和暦を返す（検算：`date.year - 2019 > 100` なので **2119 年まで「令和101年」を返す**）。設計は「無警告で `令和XX年` を返す設計は採らない」と宣言しているが、コピーしてくるコードがまさにそれを実装している。しかも技術選定 1 節は「移植した直後に差分ゼロを確認する」と書いており、**差分ゼロを達成した瞬間に設計違反になる**。未来上限の定義箇所を 1 つに統合し（`WAREKI_DISPLAY_HORIZON_YEARS` を廃止して `verifiedThrough` へ一本化）、その旨を「意図した移植差分」として明記すること。関連して `plain-date.ts` の `MAX_REFERENCE_DATE = 2200-12-31` は現行 `parseDateInput` から参照されていない（下限しか検査していない）第 3 の上限であり、これも移植時に整理対象。

- **[major] `verifiedThrough` が和暦→西暦方向に適用されるか未定義。** 13 節は「最新元号を**延長表示**しない」としか書いておらず、逆方向に触れていない。流用元 `parse-date.ts` の `buildFromEra` は `isWithinEra` を通すが、最新元号には `nextEra` が無いため **無条件 true** を返す。結果、`令和50年1月1日` は `gregorianYearOf` で 2068 年と機械換算され、**無警告で `2068年1月1日` を返す**。「未確認の改元後日付を推測変換しない」という差別化の 1 文に真正面から反する。双方向で同じ規則を適用すると明記すること。

- **[major] 4 節「正規化前後の候補数検査」の定義が曖昧で、実装が二通りに割れる。** 実入力で検証した結果を示す。
  - 報告事例 `生年月日：1987年5月14日 登録日：2020年1月1日` は、**NFKC 直後・ラベル除去前**に数えれば候補 2 件で `MULTIPLE_DATES` になる。設計 4 節の規則で防げる（流用元の現行コードでも、ラベル除去後の後段検査で 2 件になり防げている）。ここは合格。
  - しかし「正規化前」を **NFKC より前**と解釈すると穴が開く。JavaScript の `\d` は `u` フラグ下でも ASCII のみのため、全角入力 `生年月日：１９８７年５月１４日 登録日：２０２０年１月１日` の候補数は **NFKC 前で 0 件**であり、前段検査を素通りする。
  - 逆に「前後の候補数が一致すること」を要求する実装にすると、`1987年 5月 14日` や `1987 / 5 / 14`（空白除去前は候補 0 件、除去後 1 件）を誤って拒否する。

  **確定させるべき規則**：候補数は **(a) NFKC + trim の直後（情報を捨てる除去処理の前）** と **(b) 全正規化後** の 2 点で数え、**いずれかが 2 以上なら `MULTIPLE_DATES`**（`max(a, b) >= 2` で拒否、0 件は許容）。この形なら上記 3 ケースすべてが正しく処理されることを確認済み。設計 4 節・7 節をこの文言に置き換えること。

- **[major] 公開方針の推奨（選択肢2）が、未確認の事実に依存している。** Intake の確認済み事実は流用元を「**公開済み**、commit b5dc33a」と記しており、これが GitHub 公開を指すのか Chrome Web Store 公開を指すのかが確定していない。設計は最後の不確実点で「Store 公開済みのまま維持が不可避なら選択肢2は実行できない」と自ら退路を書いているが、**推奨を出す前にこの 1 事実を確認すべきだった**。年齢アプリが既に Store 公開済みなら、選択肢2 は「稼働中の公開製品を非公開化する」という重い要求に化ける。Stage 3 に入る前に事実確認を必須とし、確認結果によって推奨が選択肢3 に切り替わることを設計に明記すること。

- **[major] 差別化の 1 文が弱く、かつ「最小機能性ポリシー」と「重複コンテンツ方針」を混同している。** 2 点ある。
  1. **ポリシーの取り違え。**最小機能性ポリシーは「その拡張が実質的な機能を持つか」（ブックマークレット同然、単一サイトのラッパー等）を問うものであり、**第三者の競合が 4 本あることは最小機能性の論点ではない**。本拡張はパーサー・コンテキストメニュー・通知を持つ独立実装であり、この基準は明確に満たす。競合 4 本に対する差別化が本当に効いてくるのは「ユーザーが選ぶ理由」と、**自アカウント内の重複（出典4）**であって、両者を同じ 1 文で担保しようとしている 11 節の構成は整理が必要。
  2. **差別化文が否定形に偏っている。**「存在しない和暦や未確認の改元後日付を**推測変換しない**」は、Store の説明文としては「競合より変換できる範囲が狭い」としか読まれない。**拘束要件5 の注記こそが唯一の肯定形の差別化**である（既存 4 本は「1989年は1月7日までが昭和64年、1月8日からが平成元年」を能動的に教えない）。差別化文をこう書き換えることを推奨する。

  > 改元日の境界を検証して正確な和暦を返し、**改元のあった年は境界日を注記で示す**。全角・元年・略号・曜日付きの入力を受理し、存在しない和暦を作らない和暦変換拡張。

- **[minor] 移植対象は 4 ファイルではなく 5 ファイル。** `parse-date.ts` は `./errors.js` から `ok` / `err` / `Result` を import しており、`errors.ts` 無しでは動かない。しかし `errors.ts` は Intake の「394 行・レビュー済み 4 ファイル」に含まれていない（93+30+70+201 = 394 で一致し、`errors.ts` の分は入っていない）。さらに `errors.ts` は `REFERENCE_BEFORE_BIRTH` / `ABOVE_MAX_REFERENCE` / `SETTINGS_UNREADABLE` という年齢アプリ固有コードを含むため、**そもそも差分ゼロで移植できない**。設計のアーキテクチャ図には `domain/errors.ts` が載っているので存在自体は認識されているが、技術選定 1 節の「4 ファイルと対応テストを移植した直後に差分ゼロを確認する」という受入手順は成立しない。「移植は 5 ファイル、`errors.ts` は差分前提」と書き直すこと。

- **[minor] `eras.ts` の明治開始日 `1868-01-25` をデータから消してはならない。** Intake 出典2 が「表示側の下限をどう扱うかは別途判断が要る」と提起した点に、設計は明示的に答えていない。入力下限が `1873-01-01` であることから、実装者が「明治の開始日も 1873-01-01 でよい」と整理してしまう危険がある。`eraYearOf` は `date.year - era.start.year + 1` なので、**開始年を 1868 から動かすと明治年が全件 5 年ずれる**（検算：明治6年 = 1868+6-1 = 1873 ✓、1873 起点にすると 明治1年 になってしまう）。「開始日は元号年計算の基点であり、入力受理下限とは別概念」と設計に 1 行書くこと。

- **[minor] `MULTIPLE_DATES` コードの誤用。** 4 節規則 5 は「2 個以上のラベル区切りがあれば `MULTIPLE_DATES`」とするが、`メモ:生年月日:1987年5月14日` は日付が 1 件しかないのに「日付は1件だけ指定してください」と表示される。区切り過多は別コード（`UNPARSABLE` 相当）にするか、文言を分けること。

- **[minor] ラベルに元号名を禁じる副作用。** 規則 4 は正しい強化だが（`平成元年:1987年5月14日` の誤受理を塞ぐ）、副作用として `平成生まれ：1987年5月14日` のような自然なラベルを拒否する。誤受理ではなく誤拒否なので安全側だが、受入条件に「元号名を含むラベルは剥がさず `UNPARSABLE` とする」と明記して、テストで意図的挙動として固定すること。

- **[minor] `昭和64年1月8日` への「もしかして」提案が無い。** 拘束要件5 の経緯からして、ユーザー自身が「平成元年(昭和64年)」という直感を持っていた。同じ直感を持つ利用者は `昭和64年1月8日` を実際に入力する。現行 `buildFromEra` は `ERA_OUT_OF_RANGE` で「昭和は1926年12月25日開始、平成は1989年1月8日開始です」と返すだけで、正解を示さない。機械換算した西暦（1989-01-08）が実在日であれば「この日付は 平成元年1月8日 です」を併記できる。拘束要件5 の注記機能と実装を共有できるため追加コストは小さい。

- **[minor] 通知（`chrome.notifications`）への注記の載せ方が未定義。** basic 通知の `message` は 2 行程度で切られる。注記まで入れると主表示が埋もれる。`title` に和暦、`message` に西暦、`contextMessage` に注記の要約、といった配分を決めるか、「通知は主表示のみ・注記はポップアップで」と割り切るかを設計で確定すること。

- **[minor] 注記のアクセシビリティと「コピー対象」への含否が未定義。** 10 節の読み上げ順（入力→方向→実行→エラー→結果→コピー）に注記が入っていない。6 節の「コピー対象は正規化済みの変換結果だけ」も、注記を含めるのか含めないのかを決める必要がある（推奨：既定は和暦＋西暦の 2 行のみ、注記は含めない）。

- **[minor] 見積もりの不足。** 3 点。(1) 拘束要件5 の実装＋テストが未計上（+2〜3 時間）。(2) 「manifest・ビルド・Store 向け整理：1〜2時間」は Store 提出物（アイコン 4 サイズ、1280x800 スクリーンショット、説明文、権限ごとの用途justification、プライバシー申告）を含むと過少（実質 +3〜5 時間）。(3) E2E の「Playwright 用の事前ロード済みプロファイルと手動試験票：2〜3時間」は準備工数であり、`chrome://` / PDF / iframe / Shadow DOM / `file:` の**手動実測の実行時間**が計上されていない（+2〜4 時間）。総計は 22〜31 時間ではなく **28〜40 時間**が現実的。

- **[minor] テスト戦略の追加項目。** 現行リストは良質だが以下が欠けている。
  - 拘束要件5：1912 / 1926 / 1989 / 2019 の 4 年について、境界前後の日と**年内の無関係な日**（例：1989年12月25日）でも同じ注記が出ること。1990 年など非境界年で注記が出ないこと。
  - 元号開始日が 1 月 1 日だった場合に注記を出さないこと（後述の判定式のガード）。
  - `verifiedThrough` 超過を**和暦→西暦方向**でも同じ扱いにすること（`令和50年1月1日`）。
  - 全角コロン `：` が NFKC で `:` になり、ラベル除去が全角入力でも同じ結果になること。
  - 全角 2 日付入力が `MULTIPLE_DATES` になること（NFKC 前の候補数が 0 でも防げること）。
  - `1987年 5月 14日` / `1987 / 5 / 14` が候補数検査で誤って拒否されないこと（前段検査の過剰拒否の回帰テスト）。

## 拘束要件5（改元年の注記表示）への対応可否

**対応可能。設計の他の判断とは衝突しない。** むしろ 2 箇所で相乗効果がある。追加すべき内容は以下のとおり。

**1. 衝突の有無を検証した結果**

| 設計の既存判断 | 拘束要件5 との関係 |
|---|---|
| 3 節「年のみ入力は受理しない」（理由：1989年の正解が 2 つある） | **衝突しない。**拘束要件5 は「年月日が確定した結果」に注記を添えるものであり、年のみ入力に単一の和暦を返すわけではない。両者の前提（同一西暦年が 2 元号にまたがる）はむしろ同一である |
| 2 節「`平成元年1月7日` は変換せず期間外エラー」 | **整合。**拘束要件5 の「存在しない和暦を併記しない」と同じ原則 |
| 13 節 `verifiedThrough` で停止 | **思想が不整合。**拘束要件5 は「事実は主表示、不確かさは注記」を選んでいる。上記 blocker の修正案はこの原則に揃えるものである |
| 6 節「コピー対象は変換結果だけ」 | 注記を含めるかの判断が要る（minor で指摘） |
| 6 節 通知での結果返却 | 注記の載せ方の判断が要る（minor で指摘） |

**2. ドメイン層に必要な追加（既存 4 ファイルで足りる）**

流用元には必要な部品が全部ある。`eraForDate` / `eraYearOf` / `eraYearLabel` / `nextEra` / `previousDay` の組み合わせで書ける。新規の暦計算は不要。

判定式は「その元号の開始年が対象年と同じ」ではなく、**次の形にすること**。

```
注記を出す条件：ある元号 e が存在し、previousDay(e.start).year === 対象年 かつ e.start.year === 対象年
```

`e.start.year === 対象年` だけで判定すると、将来 1 月 1 日開始の元号が現れた場合に「その年は 2 元号にまたがる」と誤判定する（1 月 1 日開始なら前年 12 月 31 日で前元号が終わり、当年は 1 元号のみ）。また、同一年内に 2 回改元される可能性（譲位と崩御の連続など）に備え、条件に合う元号を**すべて**列挙して注記を組み立てる形にすること。

**3. 注記文言の生成と検算**

`e` を対象年に開始した元号、`p = previousDay(e.start)`、`prev` を `p` が属する元号とすると：

> `{対象年}年は{p.month}月{p.day}日までが{prev.name}{eraYearLabel(eraYearOf(prev,p))}年、{e.start.month}月{e.start.day}日からが{e.name}元年`

手計算で全境界年を検証した（すべて一致）。

| 対象年 | 生成される注記 | 検算 |
|---|---|---|
| 1912 | 7月29日までが明治45年、7月30日からが大正元年 | 1912−1868+1 = 45 ✓ |
| 1926 | 12月24日までが大正15年、12月25日からが昭和元年 | 1926−1912+1 = 15 ✓ |
| 1989 | 1月7日までが昭和64年、1月8日からが平成元年 | 1989−1926+1 = 64 ✓ 拘束要件5 の例文と完全一致 |
| 2019 | 4月30日までが平成31年、5月1日からが令和元年 | 2019−1989+1 = 31 ✓ |

**4. 受入条件として設計に追記すべき項目**

- `1989/1/8` → 主表示 `平成元年1月8日`、副表示 `1989年1月8日`、注記あり。
- `1989/1/7` → 主表示 `昭和64年1月7日`、副表示 `1989年1月7日`、**同一の注記**。
- `1989年12月25日` → 主表示 `平成元年12月25日`、**注記あり**（境界から遠い日でも年が同じなら出す。拘束要件5 の「同じ西暦年が 2 つの元号にまたがる場合のみ」の文言に忠実）。
- `1990/1/1` → 注記なし。
- **和暦→西暦方向でも同じ注記を出す**（`昭和64年1月7日` 入力、`平成元年1月8日` 入力の両方）。拘束要件5 の表示例は和暦行と西暦行の両方を含むため、方向によらず同じ結果面を使うのが自然であり、2 節の「往復変換の一致」とも整合する。
- 存在しない和暦（`昭和64年1月8日` 等）を注記にも主表示にも**併記しない**。

**5. 追加コスト**：ドメイン 1 関数＋表示整形＋テスト 10 件程度。**2〜3 時間**。

## 重要判断3件の評価

**(1) 検証済み 4 ファイルを「コピーする」判断 — 妥当。ただし前提の 2 点が誤り。**

判断そのものは支持する。2 製品・個人開発という条件で npm パッケージの常設運用費は見合わず、「3 製品目が同じ元号ドメインを使う時点、または横断反映漏れが 1 回発生した時点で再検討」という**撤退条件を先に決めている**点は特に良い。また「Store 配布物はどの方式でも製品ごとの再ビルド・再審査が必要」という指摘は正しく、共有パッケージ化のメリットを過大評価していない。

ただし前提が 2 つ間違っている。第一に、移植対象は 4 ファイルではなく **5 ファイル**（`errors.ts` が必須依存、かつ年齢アプリ固有コードを含むため差分ゼロにならない）。第二に、「移植直後に差分ゼロを確認する」という受入手順が **`era.ts` については達成してはいけない**（`WAREKI_DISPLAY_HORIZON_YEARS` を残すと設計違反になる）。受入手順を「移植直後の差分を全件列挙し、各差分に意図の根拠を添える」に改めること。

なお「改元時の修正箇所は 2 リポジトリ各 1 か所、計 2 か所」という記述は不正確。実際には `eras.ts`（開始日）に加えて `EraId` の union 型、`parse-date.ts` の `ERA_JP` 正規表現に列挙された元号名 `(明治|大正|昭和|平成|令和)`、`countDateLike` の `DATE_LIKE` 内の同じ列挙、略号 `[MTSHR]` の列挙が各リポジトリにあり、**1 リポジトリあたり実質 4 箇所**。設計の 13 節運用手順は「`EraId`、入力許可名・略号、境界テストを更新する」と正しく書いているので、技術選定 1 節の「計 2 か所」という要約のほうを直すこと。これは「元号定義は 1 ファイルだけ」という設計の主張とも食い違っている。将来の改元で**正規表現の列挙だけ更新し忘れる**のが最も起きやすい事故なので、元号名・略号の列挙は `ERAS` から動的に生成する形にすることを推奨する（コピー方式の負債を実質的に減らせる、コストの低い改善）。

**(2) 「和暦アプリのみ Store 公開、年齢アプリは手元利用」の推奨 — 論理は妥当だが、実行可能性が未確認。**

拘束要件3（別アプリとする）と出典3（3 条件一致＝統合すべき）と出典4（同一アカウント重複リスク）を同時に満たす解として、「別アプリとして作るが、公開は 1 本に絞る」は筋が通っている。3 択の比較も公平で、結論だけを書かず各選択肢の欠点を挙げている点は良い。

問題は上記 major で述べた事実未確認。加えて 2 点。

- **リスクの大きさが根拠なく決定的に扱われている。**Chrome のスパム／重複コンテンツ方針が問題にするのは「機能が重複した複数の拡張」であり、年齢アプリの主機能は年齢・年度計算、本アプリは和暦変換で、**ユーザーから見た用途は異なる**。UI と入力形式が似ていることは事実だが、それだけで制裁される確度は設計が示唆するほど高くない。設計は「審査結果を制御できない」ことを理由に最大限の安全側へ倒しているが、その代償（動作する製品を配布しない）が定量化されていない。
- **選択肢3 の評価が不当に低い。**選択肢3（和暦を先行公開し、統合は将来判断）は、**何も非公開化せずに済み、事実確認が取れるまで判断を保留できる**。設計は「統合後に説明が長くなる」を欠点として挙げるが、それは統合を実行した場合の話であって、先行公開そのものの欠点ではない。年齢アプリが既に Store 公開済みだった場合、実行可能な選択肢は 3 だけになる。**推奨を「事実確認の結果に応じて 2 または 3」とする**のが正しい。

**(3) `verifiedThrough` 超過で変換を停止する判断 — 支持しない。blocker として上記に詳述。**

問いの「利便性の損失に見合うか」への回答は **見合わない**。理由を再掲すると、(a) 誤変換のリスクは「改元が起きたとき、改元日以降の日付についてのみ」発生するのに対し、停止のコストは「改元が起きなくても、期限以降のすべての日付」に発生する。損失の範囲が非対称に大きい。(b) 契約満了日・有効期限・満期日といった数年〜数十年先の日付は和暦変換の主要ユースケースであり、これを丸ごと落とす。(c) ビルド時に凍結される値であるため、更新が止まれば今日の日付すら変換できなくなる。(d) 拘束要件5 が「主表示＋注記」という上位の解決形式を確定させており、確認期限だけが停止という強い扱いを取る整合的理由がない。

「誰がどう決めるのか」への回答：**設計に規則が無い。**現状では実装者が任意の日付を書くしかなく、更新のたびに人手で延ばす運用になる。これは既知パターン1（絶対日時のハードコード）の変種で、更新を忘れた瞬間に製品が壊れる。上記 blocker の修正案（変換は続行し注記で警告、かつ値は絶対日付ではなく導出可能な相対規則で持つ）を採ること。

## 見落とし・矛盾・前提の誤り

1. **三つ巴の未来上限。**`WAREKI_DISPLAY_HORIZON_YEARS = 100`（コピー元、和暦を 2119 年まで機械延長）／`verifiedThrough`（延長しない）／`MAX_REFERENCE_DATE = 2200-12-31`（`parseDateInput` から未参照の死んだ定数）。3 つの上限概念が同居し、設計はどれにも言及していない。1 つに統合すること。
2. **`verifiedThrough` の方向非対称。**西暦→和暦では止めるが、和暦→西暦（`令和50年1月1日` → `2068年1月1日`）は現行コードのまま無警告で通る。`isWithinEra` は最新元号に対して無条件 true を返すため、パーサー側に別途ガードが要る。
3. **改元時の修正箇所が「計 2 か所」ではない。**正規表現内の元号名・略号の列挙が別途 2 箇所ある（技術選定 1 節と 13 節の記述が互いに矛盾している）。
4. **移植対象ファイル数の誤り。**`errors.ts` が抜けており、かつ差分ゼロで移植できない。
5. **`countDateLike` の検査タイミングの曖昧さ。**「正規化前後」を NFKC 前と読むと、全角 2 日付入力が前段検査を素通りする（`\d` は ASCII のみ）。
6. **年齢アプリの Store 公開状態が未確認のまま公開方針を推奨している。**設計が自ら退路を書いているが、確認が先。
7. **最小機能性ポリシーと重複コンテンツ方針の混同**（Intake 出典5 の記述をそのまま受け継いだもの。査読としては Intake 側の整理も見直すべき）。
8. **Intake 出典2 が提起した「表示側の下限」への回答が無い。**明治開始日 `1868-01-25` を保持し続ける必要があることを設計に明記しないと、実装時に入力下限 1873 と混同して明治年が 5 年ずれる。
9. **既知パターン1（タイムボム）への言及が無い。**本アプリのドメイン層は入力日付のみを扱い時計に依存しないため実害は無いが、`verifiedThrough` を絶対日付でハードコードするとこのパターンに該当する。設計に「ドメイン層は `Date.now()` を参照しない／確認期限も絶対日時リテラルで持たない」と 1 行入れること（テスト項目の「`Date`、DOM、Chrome API をドメイン層から参照していないこと」で半分は担保されている）。

## 不確実な点・前提

- 競合 4 本の実挙動（境界日の扱い、注記の有無）は Intake の記述以上に検証していない。「注記が唯一の肯定形の差別化」という私の主張は、既存 4 本が境界日の注記を出さないという推定に立っている。Store 説明文で優位性を主張する前に、少なくとも 1〜2 本の実挙動確認を推奨する。
- `chrome.notifications` の `message` / `contextMessage` の実表示行数は OS・Chrome バージョン依存であり、注記が収まるかは実機確認が必要（設計も同種の実機確認項目を挙げている）。
- 拘束要件5 の「和暦→西暦方向でも同じ注記を出す」は、拘束要件の表示例（和暦行と西暦行が両方ある）からの私の解釈であり、ユーザーが明示的に述べたものではない。方向ごとに変える合理的理由は見当たらないが、確認の余地はある。
- 同一西暦年内に 2 回改元される事態への一般化は、明治以降の実データには存在しない（明治〜令和で年内 2 改元は 0 件）。過剰設計と見なす判断もありうるが、判定式を一般形で書くコストはほぼゼロなので推奨した。
- Chrome ウェブストアのスパム／重複コンテンツ方針の実際の運用強度（同一開発者の日付ツール 2 本が実際に制裁対象になる確度）は、私も定量的根拠を持たない。私の指摘は「設計がその確度を根拠なく高く見積もっている」ことであって、「リスクが無い」という主張ではない。
